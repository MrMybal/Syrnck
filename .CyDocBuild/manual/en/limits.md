## Workspace and versioning {#workspace}

[Named and detached HEAD](doc:native-detached) are supported. [Linked native workspaces](doc:native-workspaces) retain separate HEADs/indexes and portable backup snapshots. Partial materialization, recoverable selection changes, hard reset and stash with matching selections are available. [Archived unregistration and restoration](doc:native-workspace-archives) preserve captured dirty work, complete HEAD/index trees and context roots. [Linked relocation](doc:native-workspace-relocation) preserves the whole directory on one filesystem, with resume/abort and case changes; cross-filesystem and primary/Store moves remain work to complete. The persistent working index and observer avoid some repeated hashing but do not produce an atomic filesystem snapshot or a complete event history. Native OS events may overflow; conservative rescans and polling remain necessary.

Exact renames and explicit [edited-rename similarity](doc:native-file-history#edited-renames) are available in C++/CLI history and blame. Optional alignment covers merge, cherry-pick/revert, linear rebase, stale indexes and bidirectional native agents. Similarity is heuristic and bounded; structural conflicts stay explicit. Multiple common bases now use [bounded recursive virtual bases](doc:native-merge#recursive-bases), with explicit uncertain-path resolution. [Merge-preserving rebase](doc:native-rebase#preserve-merges) now recreates ordered parent DAGs, merge-only edits and bound conflict choices. Interactive folds refuse branch-point rewrites. Copy inference and swaps between existing paths remain unfinished. Legacy v1 revisions have no author or signature fields. Optional [v2 authorship](doc:native-authorship) records authors/committers and Ed25519 signatures; [server policies](doc:server-signatures) can authorize keys and identities. [C/Go native identity providers](doc:go-binding#native-authorship) now support signed captures/candidates and required-signature recovery without unsigned fallback. Registration is manual and policy changes require restart; [System vault signers](doc:system-vaults) are available; distributed revocation remains incomplete. Read each rebase/merge mode's constraints; available commands are not universal Git compatibility.

## Team operation and continuous synchronization {#sync}

Configured servers provide users/roles, branch checks and expiring asset leases. Native history transfer and Git catalog publication remain separate from a distributed multi-server transaction. The [resident publication agent](doc:resident-agent) captures local edits, deletions and exact renames, retains offline snapshots and retries guarded native pushes. The optional bidirectional mode applies incoming descendants through recoverable checkout and merges compatible concurrent histories. Unresolved conflicts, acknowledged remote deletions/rewinds and rewritten local history are blocked. The agent resumes only its own guarded checkout/merge transactions, including offline recovery of prepared signed targets without a private signing key. Manual or unrelated recovery stays explicit. The explicit [conflict-copy policy](doc:resident-agent#conflict-copies) preserves concurrent file contents; namespace collisions still block. OS service installation remains unfinished.

The Syncthing adapter handles regular-file block indexes/requests/responses and [pinned device connections](doc:syncthing#device-connections). A real upstream daemon is tested for differential transfers in both directions. A native-backed [folder catalog](doc:syncthing#folder-catalog) persists device index generations, version vectors, tombstones and verified files; conflicts remain explicit and historical data stays retained. Real-daemon reconnection after an offline rename is tested. The [continuous controller](doc:syncthing#folder-controller) now applies regular files/tombstones to actual native workspaces, with owned recovery and live-daemon reconnection tests. Explicit [concurrent-version copies](doc:syncthing#protocol-conflicts) merge regular-file vectors while retaining different losing contents. Directory/symlink metadata, OS service installation, discovery, a pairing UI, catalog membership management and automatic history retirement remain unfinished.

## Security, retention and recovery {#security}

Objects can be encrypted at rest, with separately keyed backups/restores. The [password-protected key API](doc:api-password-keys) provides bounded Argon2id derivation and authenticated envelopes. [CLI key files](doc:key-files) support creation, existing-key protection and password changes; C/Go opaque native owners open short Store sessions without exporting unwrapped keys. The standalone BEP CLI also supports a protected key file, authenticated once at startup; restarting reloads changed credentials. Ordinary transfers give plaintext objects to trusted servers. The explicit [sealed C++/C/Go snapshot APIs and C++/CLI transfers](doc:sealed-repositories) provide opaque encrypted snapshots, differential ciphertext reuse and retained-client freshness checkpoints; the master key stays on clients. The native resident agent supports this transport explicitly with `--sealed --wire PATH`, including guarded bidirectional merges. The [Syncthing untrusted-device mode](doc:syncthing#untrusted) uses its own password/format to exchange encrypted files with an upstream receive-encrypted daemon; it does not carry sealed Syrnck revision snapshots. First-contact root trust remains unfinished. [Protected signing-seed providers](doc:signing-keys) are available in C++/CLI/C/Go and both resident services. [System key vaults](doc:system-vaults) now support CLI and native/service owners with protected recovery copies. Distributed rotation/revocation, automatic replica repair and distributed GC remain unfinished. Sealed history still retains all previous carrier snapshots; changing an envelope password does not retire their keys or bytes.

Retention is explicit. Archives preserve versions until their protecting roots are retired; a verified backup can protect manual retirement, but automatic age/release policies are not implemented. Process interruption and power-loss durability are different guarantees. No operation establishes universal power-loss, network-filesystem or hostile external-writer safety.

Explicit [active-checkout edit preservation](doc:syncthing#active-checkout-edits)
archives regular-file contents before conflict-copy moves and resumes the strict
owned journal. Missing-file/deletion intent and ambiguous namespace changes still
need resolution. The retained edit archive groups currently require manual
retention management; automatic age/backup-based retirement remains unfinished.

The separate [opaque BEP receiver](doc:syncthing#opaque-receiver) now retains encrypted metadata/blocks without a folder password and resumes complete block receipts. Its standalone role serves one configured peer; multi-peer CLI orchestration, incomplete-receipt retirement and private conflict resolution remain separate work.

[Verified in-place repair](doc:storage-repair) now recovers missing/corrupt loose and packed payloads from a backup or healthy local alternate copy. It preserves retained roots and unaffected packs; automatic remote replica repair remains separate work.
